# Подготовка адаптера Huawei Dorado без оборудования

## Краткий вывод

Без массива можно продолжить исследование протокола и подготовить локальные
проверки. Целевая модель, firmware, pool и transport остаются
невыбранными. Значение `supported=false` сохраняется; положительного профиля
Huawei для наших checkpoints пока нет.

Для исследования найден конкретный первичный источник: официальный
[Huawei OpenStack Driver v26.2.0](https://github.com/Huawei/OpenStack_Driver/tree/bda6d13cd0147648e04da5479d678dc2e0541395/Cinder/Epoxy),
каталог `Cinder/Epoxy`. В нём есть native rollback, отсутствующий в Huawei-классе
из нашего исходного архива Cinder. Это отдельная реализация поставщика, а не
обновление уже подготовленного C1.1 и не доказательство совместимости с ним.

Ближайший полезный результат — спецификация протокольных проверок на основе
этого исходника. Полный адаптер требует также решения восстановления составных
операций и подтверждаемой связи результата с UUID текущего шага. Одного
переноса `revert_to_snapshot` для этого недостаточно.

## Что установлено по коду поставщика

В [`huawei_base_driver.py`](https://github.com/Huawei/OpenStack_Driver/blob/bda6d13cd0147648e04da5479d678dc2e0541395/Cinder/Epoxy/huawei_base_driver.py#L880-L882)
метод `revert_to_snapshot` вызывает отдельный flow отката. Создание snapshot
по-прежнему включает отдельную активацию после create.

Ниже перечислены вызовы относительно базового URL устройства. Это контракт,
наблюдаемый в клиентском коде, а не полная REST-спецификация массива.

| Операция | HTTP и путь | Поля запроса или чтения |
|---|---|---|
| Создать snapshot | `POST /snapshot` | `NAME`, `DESCRIPTION`, `PARENTID` |
| Активировать | `POST /snapshot/activate` | `SNAPSHOTLIST` |
| Остановить | `PUT /snapshot/stop` | `ID` |
| Удалить | `DELETE /snapshot/{id}` | ID в пути |
| Запустить rollback | `PUT /snapshot/rollback` | `ID`, `ROLLBACKSPEED` |
| Прочитать snapshot | `GET /snapshot/{id}` | Состояние объекта |
| Найти по имени | `GET /snapshot?filter=NAME::{name}&range=[0-100]` | Первый элемент ответа в текущем клиенте |

Основание: [`Snapshot` в rest_client.py](https://github.com/Huawei/OpenStack_Driver/blob/bda6d13cd0147648e04da5479d678dc2e0541395/Cinder/Epoxy/rest_client.py#L279-L377).

В [`huawei_flow.py`](https://github.com/Huawei/OpenStack_Driver/blob/bda6d13cd0147648e04da5479d678dc2e0541395/Cinder/Epoxy/huawei_flow.py#L918-L976)
откат запускается для активного snapshot; при состоянии rolling back flow
переходит к ожиданию. Завершение определяется через `HEALTHSTATUS`,
`ROLLBACKRATE` и `ROLLBACKENDTIME`. Запрос rollback не передаёт UUID нашего
checkpoint step, а flow не сопоставляет прочитанное завершение с таким UUID.

Это ограничение доказательства, а не установленная неисправность массива:
опубликованный клиент не доказывает, что после потери ответа можно отличить
новый откат от предыдущего отката того же snapshot. Возможность другого
server-side API для такой проверки остаётся открытой.

## Что нельзя переносить в checkpoint без отдельного решения

**Повтор мутации.** Общий
[`rest_operation_wrapper`](https://github.com/Huawei/OpenStack_Driver/blob/bda6d13cd0147648e04da5479d678dc2e0541395/Cinder/Epoxy/rest_client.py#L1726-L1783)
после ошибки запроса может выполнить relogin и снова вызвать исходный метод.
Этот wrapper применяется также к POST, PUT и DELETE. Для checkpoint после
неопределённого исхода требуется `unknown` и последующее наблюдение результата;
разрешение повтора должно опираться на подтверждённую идемпотентность сервера.

**Составные эффекты.** Create и activate, а также stop и delete являются
отдельными мутациями. В C1.1
`reconcile` (`../../work/cinder-checkpoint-continuation/cinder/checkpoints/continuation_manager.py`)
только запрашивает результат уже начатого шага; он не отправляет недостающую
мутацию. Поэтому восстановление после остановки между create и activate
нельзя реализовать скрытым вызовом activate из query.

**Подтверждение именно текущей операции.** Имя snapshot и его последний статус
помогают найти объект, но сами по себе не подтверждают завершение конкретного
повторного revert. Для допуска нужны привязка к операции, проверка родительского
LUN и принадлежности объекта, а также определённое поведение после исчезновения
истории операций.

**Неполный ответ.** В условии поставщика `ROLLBACKENDTIME`, полученное через
`dict.get`, сравнивается с `'-1'`. Если поле отсутствует, это сравнение истинно.
Будущий checkpoint parser должен явно проверять наличие, типы и смысл
обязательных полей. Это статическое наблюдение о Python-условии; получение
такого ответа от реального Dorado не установлено.

## Варианты дальнейшей работы

| Вариант | Что даёт | Ограничение |
|---|---|---|
| Исследовать минимальный checkpoint transport и parser отдельно | Позволяет проверить формы запросов, отсутствие слепого повтора и отказ на неполных ответах | Не решает сам по себе продолжение составных эффектов и аппаратную квалификацию |
| Заменить текущий Huawei-драйвер полным драйвером поставщика | Добавляет его обычный native rollback и другие функции | Широкое изменение; не устраняет разрывы checkpoint recovery |
| Сначала расширить Cinder durable substeps | Может дать явные права на продолжение create/activate и stop/delete | Новый архитектурный этап; необходимость и детали зависят от полного vendor API |

Для ближайшей спецификации рекомендован первый вариант. Полная замена драйвера
не нужна для изучения протокола. Расширение Cinder следует проектировать отдельно,
если документация не подтвердит подходящую серверную операцию с устойчивым
идентификатором и наблюдаемым завершением. Здесь эта развилка не закрыта.

## Проверки без массива

Это требования к будущим протокольным тестам, а не результаты уже выполненных
тестов. Ответы должны иметь пометку `synthetic`, исходную ссылку и перечисленные
предположения. Настоящие записи с оборудования остаются отдельной категорией.

| Сценарий | Ожидаемая проверка |
|---|---|
| Потерян ответ на POST или PUT | Повторной мутации нет, исход сохраняется неопределённым |
| Повторное чтение после timeout или relogin | Query не вызывает snapshot/revert/delete |
| Snapshot найден по имени, но parent или owner отличаются | Объект не присваивается и не удаляется |
| Пустой, частичный или неверно типизированный ответ | Нет ложного success или failed_no_effect |
| Сохранён результат старого revert того же snapshot | Он не принимается за подтверждение нового step UUID |
| Процесс остановлен после create, до activate | Нет ложного available; частичный результат остаётся защищённым |
| Процесс остановлен после stop, до delete | Нет ложного удаления и освобождения квоты |
| Изменён payload при том же ключе операции | Запрос отклоняется до внешнего эффекта |
| Query не может восстановить связь с исходной операцией | Unknown сохраняет защиту; новая мутация не подставляется вместо доказательства |
| Нет подтверждённого профиля | Обычный admission C1.1 остаётся закрытым |

Синтетические проверки могут доказать свойства нашей реализации. Утверждения
о CoW/ROW, сохранении других snapshots и WWN, повторном откате A/B/A, поведении
контроллеров и длительности паузы требуют документации целевого firmware и
последующей проверки на устройстве. Полная V1 дополнительно проверяет реальную
RAM и все диски ВМ.

## Результат подготовки

Зафиксированы исходник native rollback, формы запросов и разрывы между обычным
драйвером и C1.1. Модель/firmware у пользователя больше не являются необходимым
входом для этого статического этапа: исследование привязано к версии исходника,
а не к выдуманной конфигурации массива.

Реализация D1 и протокольных тестов ещё не начата. Product code, runtime profiles
и существующие bundles не изменены. Этот результат дополняет
[общую подготовку Dorado/TATLIN](2026-10-08-checkpoint-vendor-readiness.md);
он не закрывает D1/D2 или аппаратную приёмку.
