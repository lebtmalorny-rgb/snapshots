# RAM checkpoints ВМ на Huawei Dorado и YADRO TATLIN: вывод по форкам Nova/Cinder

**Дата:** 2026-10-06  
**Целевые СХД:** Huawei Dorado и YADRO TATLIN; конкретные модели и версии ПО пока не определены.  
**Основание:** [исследование RAM snapshots](openstack_vm_snapshot_ram_nova_extension.md), исходники из `nova-pvs.zip` и `cinder-pvs.zip`, официальные материалы производителей и OpenStack.

## Краткий вывод

Первый рабочий вариант следует проектировать для **Cinder-backed ВМ на целевых СХД**. Нужна согласованная доработка Nova, Cinder и соответствующих storage drivers.

Общая схема: **Nova управляет RAM/runtime state и жизненным циклом checkpoint; Cinder управляет снимками и откатом дисков; драйверы реализуют операции конкретных массивов.**

Главное ограничение обнаружено в драйверах предоставленного архива:

- Huawei использует снимки на стороне СХД и реализует групповые операции, но собственного метода отката `revert_to_snapshot` в этом драйвере нет.
- TATLIN создаёт snapshot посредством полного копирования данных в отдельный том. Групповые согласованные снимки отключены, собственного `revert_to_snapshot` также нет.
- Для обоих драйверов общий механизм Cinder предусматривает откат копированием данных в исходный том. Это не подтверждает поддержку быстрого отката средствами массива.

**Возможности драйверов из архива необходимо отличать от возможностей самих СХД и других версий вендорских драйверов.** Поддержка требуемого checkpoint на конкретной конфигурации ещё не доказана.

## Уточнение от 2026-10-11: драйверы уже есть

В исходном `cinder-pvs.zip` присутствуют драйверы Huawei
(`cinder/volume/drivers/huawei/`) и YADRO TATLIN
(`cinder/volume/drivers/yadro/tatlin_*.py`). Термин «адаптер массива» в следующих
этапах означает доработку этих драйверов под наш checkpoint-контракт.
Создавать весь драйвер с нуля не требуется.

В подготовленных патчах Cinder базовый `VolumeDriver` уже содержит
`get_checkpoint_capabilities`, `checkpoint_create_snapshot`,
`checkpoint_revert_to_snapshot`, `checkpoint_delete_snapshot` и
`checkpoint_query_operation`. В Huawei/TATLIN эти методы пока не
переопределены: capabilities сообщает `unsupported_driver`, а четыре
операционных метода выбрасывают `CheckpointNotSupported`.

Следующая задача — использовать имеющиеся операции драйвера и реализовать
недостающие создание, откат и удаление checkpoint-снимков, а также проверку
результата операции после потери ответа. Проверка результата не должна
повторять изменение на массиве. Для TATLIN отдельно требуется установить,
какой native snapshot/revert API или версия драйвера обеспечит нужную
семантику вместо архивного полного копирования. RAM остаётся ответственностью
Nova/libvirt; поддержка checkpoint для конкретной СХД требует стендовой проверки.

## 1. Что подтверждено исходниками

| Возможность | Huawei в архиве | TATLIN в архиве |
|---|---|---|
| Создание snapshot | Вызовы создания и активации snapshot на массиве | Полное копирование исходного тома в отдельный backend volume |
| Групповой snapshot | Есть реализация: создание снимков и активация их списка | `consistencygroup_support = False`, `consistent_group_snapshot_enabled = False` |
| Собственный `revert_to_snapshot` | Не реализован | Не реализован |
| Общий путь отката Cinder | Временный том из snapshot → копирование в исходный том | Временный том из snapshot → копирование в исходный том |
| Выбор произвольного старого snapshot через существующий API | Запрещён общей проверкой Cinder: допустим только latest snapshot | То же ограничение |

### Huawei

В common.py (`sources/cinder-pvs/cinder/volume/drivers/huawei/common.py`), строки 835–865, `create_snapshot()` создаёт и активирует snapshot через REST-клиент массива.

В том же файле, строки 1695–1740, реализован `create_group_snapshot()`: сначала создаются отдельные snapshots, затем их список передаётся на активацию. Запрос к массиву виден в rest_client.py (`sources/cinder-pvs/cinder/volume/drivers/huawei/rest_client.py`), строки 307–313.

Наличие такого кода не доказывает атомарность групповой операции на любой модели Dorado и любой версии ПО. Это необходимо подтвердить для целевой конфигурации.

### TATLIN

В tatlin_common.py (`sources/cinder-pvs/cinder/volume/drivers/yadro/tatlin_common.py`):

- строки 438–457: `create_snapshot()` создаёт временный объект тома и вызывает `create_cloned_volume()`;
- строки 284–344: клонирование создаёт backend volume и копирует данные через `volume_utils.copy_volume(..., sparse=False)`;
- строки 562–563: поддержка consistency groups и consistent group snapshots объявлена отключённой.

Таким образом, snapshot в этой реализации — **полная копия данных, а не моментальный CoW-снимок**. При согласовании RAM и дисков за счёт остановки записей ВМ время остановки будет включать копирование дисков. Это существенное ограничение для целевого сценария.

### Общие ограничения Cinder

В volumes.py (`sources/cinder-pvs/cinder/api/v3/volumes.py`), строки 225–258, API `revert` принимает только последний snapshot тома.

В volume/api.py (`sources/cinder-pvs/cinder/volume/api.py`), строки 386–411, откат требует состояния тома `available` и snapshot `available`.

Базовый driver.py (`sources/cinder-pvs/cinder/volume/driver.py`), строки 2312–2322, выбрасывает `NotImplementedError` для отсутствующей реализации `revert_to_snapshot`. В manager.py (`sources/cinder-pvs/cinder/volume/manager.py`), строки 1124–1169, Cinder обрабатывает это через создание временного тома из snapshot и копирование данных в исходный том.

Общий путь не создаёт замену исходному Cinder volume как результат отката, однако успешное сохранение идентификаторов и восстановление RAM вместе с подключениями дисков требуют отдельной проверки на стенде.

## 2. Возможности TATLIN за пределами архивного драйвера

В официальном сообщении от 20 августа 2024 года YADRO описывает для TATLIN.UNIFIED v3.1:

- мгновенные снимки отдельных ресурсов и групп ресурсов;
- механизм Redirect-on-Write и пулы косвенной адресации;
- клоны, первоначально ссылающиеся на блоки снимка;
- интеграцию управления мгновенными снимками с OpenStack через TATLIN.SATELLITES.

Источник: [YADRO — обновление ПО TATLIN.UNIFIED v3.1](https://yadro.com/ru/press/yadro-vypustila-bolshoe-obnovlenie-po-dlya-sistem-khraneniya-dannykh-tatlinunified/).

Следовательно, использование полного копирования в предоставленном драйвере **не означает отсутствия мгновенных снимков у TATLIN**. Нужно установить, какой вендорский драйвер и какая версия ПО будут использоваться. Заявление об интеграции с OpenStack само по себе не подтверждает откат к произвольному snapshot с сохранением исходного volume UUID.

Redirect-on-Write также следует отдельно сопоставить с формулировкой требования «Copy-on-Write»: автоматически объявлять буквальное соответствие этих терминов нельзя.

## 3. Предлагаемое направление реализации

1. **Nova:** отдельная сущность `InstanceCheckpoint`, API создания/просмотра/отката/удаления, хранение RAM и runtime state, координация дисковых снимков, блокировка конфликтующих операций и восстановление после частичных ошибок.
2. **Cinder:** проверяемый контракт возможностей backend, откат к выбранному snapshot с сохранением volume UUID, управление состояниями и согласование операций над всеми дисками checkpoint.
3. **Huawei и YADRO drivers:** использование снимков и отката средствами СХД там, где это подтверждено документацией и реализацией соответствующей версии драйвера. Недоступная возможность должна явно сообщаться до начала checkpoint.

Для RAM и дисков нужна одна согласованная точка восстановления. Простая последовательность независимых snapshots работающей ВМ этого не гарантирует. Точный порядок остановки записей, завершения дисковых I/O, сохранения RAM, создания snapshots и возобновления ВМ необходимо определить в проекте реализации.

Место хранения RAM checkpoint также требует отдельного решения: наличие блочной СХД само по себе не задаёт общее файловое хранилище, доступное libvirt.

**Рекомендуемый следующий шаг:** определить целевые драйверы и подтвердить их операции snapshot/revert; затем зафиксировать подробный контракт Nova ↔ Cinder ↔ driver. Полное копирование в архивном TATLIN driver не следует считать выполнением требования моментального CoW-снимка.

## 4. Что требуется уточнить

- Конкретные модели Dorado и TATLIN, версии ПО массивов и используемые типы пулов.
- Драйверы из архива или отдельные вендорские пакеты; их версии и исходники.
- Протокол подключения: FC или iSCSI.
- Возможность отката к произвольному snapshot без замены исходного тома; влияние на более новые snapshots и клоны.
- Допустимое время остановки ВМ и расположение RAM checkpoint store.

Эти параметры пока не согласованы. Предложенное разделение компонентов является направлением проектирования, а не утверждённой спецификацией реализации.
