# Итог исследования и разработки на 2026-10-10

Уточнение документации о существующих драйверах: 2026-10-11.

## Вывод

Архитектура checkpoint разделена между Nova и Cinder. Nova управляет состоянием
ВМ, RAM и общей последовательностью операции; Cinder отвечает за защищённые
дисковые операции и подключения. Продуктовая часть оформлена в 40 патчей.
Для законченной функции на Dorado/TATLIN ещё нужны доработка уже имеющихся
драйверов Cinder под checkpoint-контракт и испытания на конкретных массивах.

## Реализованная часть

| Часть | Результат |
|---|---|
| Nova N1 | API и модель checkpoint, журналы, квоты, запреты конфликтующих операций, recovery |
| Nova N2 | Исполнитель, RAM/runtime-артефакты, libvirt save/restore, координация дисков и восстановление подключений |
| Nova fixes | Нормализация attachment connection info, поиск claimed child effects, namespace libvirt metadata |
| Cinder C1 | API и driver contract, журналы операций, резервирование и защита ресурсов |
| Cinder C1.1 | Scoped continuation и attachment requests, сервисное продолжение операций |

Продуктовые версии: Nova `c524d80e5fe26020905b3fc511b06100180f0836`,
Cinder `d065a55cbe5cb8cd59489752846a41145d72bd27`.
Подробные исходные стадии и trees приведены в [MANIFEST](../MANIFEST.json).

## Где заканчивается доказанный результат

Сохранённый отчёт прогона от 2026-10-10 фиксирует успешные direct libvirt
и native runtime gates и 10/10 целевых Linux-тестов. Проверена настоящая RAM
локального гостя QEMU/libvirt; дисковые операции моделировались, у гостя нет
реальных дисков. Код этого прогона: `15f723d1bfcd4a0d2440ad32fa03e2e537b3e4fa`.

Полный Linux suite 198/198 и матрица L1-R 13/13 — отдельные исторические
проверки, а не повторный полный прогон финального кода. При подготовке
этого компактного комплекта проверены применение патчей, итоговые trees
и целостность файлов; Docker и функциональные тесты заново не запускались.
Краткий снимок существующих результатов — [validation-summary.json](validation-summary.json).
Полные логи и RAM-артефакты остались в ранее сохранённом большом комплекте.

Поддержка СХД, совместная согласованность RAM и реальных дисков, KVM и
production topology не квалифицированы. Feature default-off;
`hardware_qualified=false`, `production_qualified=false`.

## Выводы по хранилищам

Драйверы Huawei и YADRO TATLIN присутствуют в исходном `cinder-pvs.zip`:
`cinder/volume/drivers/huawei/` и `cinder/volume/drivers/yadro/tatlin_*.py`.
Под «адаптером массива» здесь понимается доработка этих драйверов с
использованием готовых операций. Создавать весь драйвер с нуля не требуется.

В базовом `VolumeDriver` подготовленного Cinder уже определены
`get_checkpoint_capabilities`, `checkpoint_create_snapshot`,
`checkpoint_revert_to_snapshot`, `checkpoint_delete_snapshot` и
`checkpoint_query_operation`. Huawei/TATLIN их пока не переопределяют:
capabilities сообщает `unsupported_driver`, а операционные методы
выбрасывают `CheckpointNotSupported`. Следующая задача — реализовать эти
методы для выбранного массива, включая проверку результата после потери
ответа без повторного изменения на СХД. RAM сохраняет и восстанавливает
Nova/libvirt.

- В предоставленном Huawei driver есть native snapshot primitives, но нет
  собственного `revert_to_snapshot` и checkpoint hooks. Составные операции
  create/activate и stop/delete требуют явного восстановления после сбоев.
- В предоставленном TATLIN driver snapshot реализован полным копированием;
  согласованные групповые снимки отключены. Это характеристика данного
  исходника, а не всех версий TATLIN.
- В отдельно исследованном официальном Huawei Driver v26.2.0 найден native
  rollback. Он не переносился в продуктовые патчи автоматически и сам по себе
  не подтверждает checkpoint-контракт.
- Обычный retry mutating HTTP-запроса после потери ответа недостаточен:
  неизвестный исход должен оставаться unknown до подтверждённого readback.
- Отдельный D1-P уже существует как локальный пакет проверки протокола на
  синтетических ответах. Это не Cinder adapter; `supported=false`. Его код
  и лаборатория не входят в данный набор продуктовых патчей.

Без доступа к СХД разумная точка остановки — данный набор патчей и
зафиксированные требования к backend. После появления массива потребуются
точные модель/firmware/драйвер, реализация native effects и один сквозной
сценарий: checkpoint → изменение RAM и дисков → откат той же ВМ → проверка
данных, памяти и идентификаторов, затем проверки частичных сбоев.
