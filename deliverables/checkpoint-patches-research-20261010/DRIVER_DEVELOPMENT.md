# Как доработать драйверы Huawei и TATLIN для checkpoint ВМ

Дата: 2026-10-11. Руководство относится к опубликованным патчам Nova N1/N2
и Cinder C1/C1.1. Оно описывает предстоящую разработку; vendor checkpoint-методы
пока не реализованы. Обычные драйверы обоих производителей уже есть в
`cinder-pvs.zip`.

## 1. Что можно сделать без массива

Документация производителя — основной источник сведений о командах,
параметрах, ограничениях и завершении операций. По ней можно разработать
протокол, написать доработку драйвера и проверить обработку ответов на локальных
тестах. Отсутствие оборудования само по себе не запрещает эту работу.

Стенд нужен для следующего этапа: подтвердить, что реализация на конкретных
модели и firmware сохраняет данные, корректно переживает сбои и согласуется
с восстановлением RAM. Это отдельный результат от готовности кода.

Для Huawei использовать три источника совместно:

| Источник | Что из него брать |
|---|---|
| REST Interface Reference для выбранной версии Dorado | HTTP methods/paths, обязательные поля, типы, коды ошибок, асинхронные jobs, query и правила повторов |
| HyperSnap Feature Guide for Block | Семантика снимков и rollback, ограничения LUN, snapshot groups, совместимость с другими функциями |
| Официальный Huawei OpenStack Driver | Практическое сопоставление Cinder objects с LUN/snapshot, формирование запросов, проверка ответов |

Официальный [каталог Huawei для Dorado](https://info.support.huawei.com/enterprise/jp/multilingual-document/oceanstor-dorado-series-pid-262794301)
перечисляет REST Interface Reference для 6.1.x и V700R001 и руководства
HyperSnap. Выбирать нужно согласованные версии документов; сведения о NAS
snapshots нельзя автоматически применять к блочным LUN.

Исследование проекта уже разобрало официальный Huawei Driver v26.2.0,
commit `bda6d13cd0147648e04da5479d678dc2e0541395`: найден native rollback,
описаны его вызовы и ограничения восстановления. См.
[исследование Huawei без оборудования](research/2026-10-08-dorado-without-hardware.md).

При проверке 2026-10-11 подтверждено наличие указанных руководств в каталоге
и повторно прочитан официальный код rollback. Полный текст REST Interface
Reference в этой проверке получить не удалось. Поэтому наличие request key,
истории jobs и точные гарантии повторных запросов здесь не объявляются
подтверждёнными. Неполученный документ или отсутствие функции в клиентском
коде не доказывают отсутствия этой функции у массива.

Практический порядок: выбрать документированную целевую версию → выписать
контракт операций → реализовать и проверить код локально → испытать его на
соответствующей СХД. Неясные пункты сначала искать в REST/HyperSnap/Command
Reference и документации ошибок; оставшиеся вопросы фиксировать отдельно.

## 2. От какой версии кода начинать

Сначала применить комплект по [APPLY.md](APPLY.md).
Доработка драйвера строится поверх **всех 17 патчей Cinder C1 → C1.1**.

| Компонент | Контрольная версия |
|---|---|
| Cinder C1.1 | commit `d065a55cbe5cb8cd59489752846a41145d72bd27` |
| Итоговый Cinder tree | `53888d9cea7fa1b12d35a0b9afd894eeee270843` |
| Nova с интеграционными исправлениями | commit `c524d80e5fe26020905b3fc511b06100180f0836` |
| Итоговый Nova tree | `5e968fbae851c47b321991e8cccd573b06e7e362` |

После `git am` commit IDs могут отличаться; проверять нужно tree.
В чистом отдельном checkout Cinder до начала доработки:

```sh
git status --short
git rev-parse 'HEAD^{tree}'
git branch checkpoint-c11-base
git switch -c feature/huawei-checkpoint-driver
```

Ожидаемый tree указан выше. Локальную ветку `checkpoint-c11-base` создать
один раз как точку сравнения. Для TATLIN использовать отдельную ветку от
той же базы. Исходные патчи и их manifests сохранять без изменений.

## 3. Где находится код

Все следующие пути относительны корню Cinder после применения патчей.

| Файл или каталог | Назначение при доработке |
|---|---|
| `cinder/volume/driver.py` | Сигнатуры пяти методов checkpoint и безопасное поведение по умолчанию |
| `cinder/checkpoints/contracts.py` | Точная схема capabilities и допустимые результаты драйвера |
| `cinder/checkpoints/manager.py` | Dispatch/query C1, проверки профиля и принадлежности объектов |
| `cinder/checkpoints/continuation_manager.py` | Те же операции в сервисном контексте C1.1 |
| `cinder/db/sqlalchemy/checkpoints.py` | Claim шага до I/O, сохранение результата, защита ресурсов и квоты |
| `cinder/volume/drivers/huawei/common.py` | `HuaweiBaseDriver`, общие операции Huawei |
| `cinder/volume/drivers/huawei/rest_client.py` | Запросы к массиву, login и повтор запросов |
| `cinder/volume/drivers/huawei/huawei_driver.py` | `HuaweiISCSIDriver` и `HuaweiFCDriver`, подключения томов |
| `cinder/volume/drivers/yadro/tatlin_common.py` | `TatlinCommonVolumeDriver`, общие операции TATLIN |
| `cinder/volume/drivers/yadro/tatlin_client.py`, `tatlin_api.py` | Клиент TATLIN и HTTP-транспорт |
| `cinder/volume/drivers/yadro/tatlin_fc.py`, `tatlin_iscsi.py` | Варианты подключений TATLIN |
| `cinder/tests/unit/checkpoints/fake_driver.py` | Пример формы контракта для тестов; хранит состояние только в памяти |
| `doc/source/admin/checkpoint-contract.rst`, `checkpoint-continuation.rst` | Эксплуатационные границы C1/C1.1 |

Общую логику checkpoint разумно размещать в общей части драйвера либо в
отдельном внутреннем модуле, вызываемом из неё. FC/iSCSI-классы должны
наследовать одинаковые правила checkpoint; особенности транспорта проверяются
отдельно. RAM, libvirt, квоты и общий жизненный цикл ВМ остаются в существующих
Nova/Cinder компонентах.

## 4. Какие методы реализовать

Сигнатуры из `VolumeDriver`:

```python
def get_checkpoint_capabilities(self, context, volume): ...

def checkpoint_create_snapshot(self, context, volume, snapshot,
                               operation_id): ...

def checkpoint_revert_to_snapshot(self, context, volume, snapshot,
                                  operation_id): ...

def checkpoint_delete_snapshot(self, context, volume, snapshot,
                               operation_id): ...

def checkpoint_query_operation(self, context, volume, snapshot,
                               operation_id, action): ...
```

Здесь **`operation_id` — UUID конкретного Cinder checkpoint step**.
Manager передаёт `step.id`, а не UUID всей операции Nova или checkpoint.
Аргумент `action` в query принимает `snapshot`, `revert`, `delete_snapshot`.

| Метод | Обязанность |
|---|---|
| `get_checkpoint_capabilities` | Проверить свойства данного тома и фактический профиль backend, вернуть подтверждённые возможности либо отказ |
| `checkpoint_create_snapshot` | Создать native snapshot выбранного тома; подтвердить его готовность именно для этого шага |
| `checkpoint_revert_to_snapshot` | Восстановить выбранную, в том числе старую, точку в исходный том с сохранением требуемой идентичности и остальных checkpoints |
| `checkpoint_delete_snapshot` | Удалить только выбранный checkpoint snapshot, сохранив текущие данные и другие точки |
| `checkpoint_query_operation` | Установить исход ранее отправленного шага без повторной мутации массива |

Обычные `create_snapshot`, `delete_snapshot`, `revert_to_snapshot` не
подключаются к этому контракту автоматически. В частности, простой возврат
`self.create_snapshot(snapshot)` имеет другой формат результата и не решает
проблему неизвестного исхода или составных операций.

## 5. Точная схема capabilities

`contracts.validate_capabilities()` допускает только следующий набор полей:

| Поле | Требование для положительного ответа |
|---|---|
| `contract_version` | Целое `1` |
| `supported` | Именно boolean `true` |
| `native_snapshot` | `true` |
| `snapshot_semantics` | `cow` или `row`, согласно выбранному профилю |
| `arbitrary_inplace_revert` | `true` |
| `preserves_other_checkpoints` | `true` |
| `independent_snapshot_delete` | `true` |
| `operation_reconciliation` | `true` |
| `consistent_group_snapshot` | Boolean; `false` допустим, групповые снимки не являются обязательной capability C1 |
| `driver_identity` | Ровно `driver_class`, `driver_version`, `profile`: непустые строки длиной до 255 символов |
| `unsupported_reasons` | Пустой список `[]` |

Лишние поля также отвергаются. Модель, firmware, pool, vStore и transport
проверяются реализацией профиля; добавлять их произвольно в этот JSON нельзя.
Недостаточно объявить `supported=true` по имени класса драйвера.

Для неподтверждённого профиля использовать существующий helper:

```python
from cinder.checkpoints import contracts

capabilities = contracts.unsupported_capabilities('unverified_profile')
```

Положительные fixtures допустимы в тестах. Реальный разрешающий профиль
появляется после проверки реализации и соответствующей конфигурации массива.
Смена `driver_identity` после reserve блокируется worker как
`driver_profile_changed`; существующая защита сохраняется.

Исследовательский [шаблон профиля](research/2026-10-08-checkpoint-vendor-profile.template.json)
служит анкетой для сбора сведений. Он не загружается в Cinder как готовая
runtime-конфигурация. Его исторические dependency pins сверять с разделом 2.

## 6. Формат результатов и неизвестный исход

Четыре операционных метода возвращают словарь. Допустимы ровно поля
`status`, необязательные `backend_reference` и `error_code`.

| `status` | Когда возвращать |
|---|---|
| `succeeded` | Доказано завершение именно запрошенного эффекта над правильными объектами |
| `pending` | Подтверждено выполнение этой операции, терминальный исход пока не достигнут |
| `failed_no_effect` | Доказано, что эффекта не было и он уже не сможет появиться |
| `unknown` | Доказательств недостаточно, включая потерю ответа и неоднозначное состояние |

`backend_reference` — непустая строка до 1024 символов.
`error_code` соответствует `[a-z][a-z0-9_]{0,63}` и запрещён при `succeeded`.
Не возвращать vendor response целиком, traceback, пароль или токен.
Неверный формат автоматически превращается в
`unknown / invalid_driver_result`.

Примеры формы ответа:

```json
{"status": "pending", "backend_reference": "opaque-native-job-reference"}
```

```json
{"status": "unknown", "error_code": "native_result_unconfirmed"}
```

Timeout, HTTP 500, обрыв соединения, ошибка разбора JSON и отсутствие объекта
при первом чтении не доказывают `failed_no_effect`. HTTP 2xx сам по себе
не доказывает завершение асинхронной операции. Для удаления HTTP 404 можно
трактовать только с учётом документированной семантики, правильного объекта,
его принадлежности и состояния операции.

## 7. Идентичность и сохранение связи с операцией

До реализации выписать способ восстановления соответствия:

```text
Cinder step UUID + action + volume UUID + snapshot UUID
    ↔ array/vStore + source LUN identity + native snapshot identity
    ↔ конкретная native operation/job
```

Нужны проверки parent LUN, owner/namespace и устойчивых native identifiers.
Имя snapshot удобно для поиска, но одного совпадения имени недостаточно.
Два результата поиска, чужой parent или неполный ответ должны давать отказ
или `unknown`, а не выбор первого объекта.

`backend_reference` сохраняется в `CheckpointStep` после ответа драйвера.
Query получает `volume, snapshot, step UUID, action`; native job ID отдельным
аргументом не передаётся. Следовательно, связь должна восстанавливаться после
restart и потери первого ответа. Сначала искать документированный серверный
request key/lookup; если его нет, проектировать защищённое долговечное
соответствие и доказательство исхода. Одна запись job ID после ответа
не закрывает окно «массив выполнил запрос, ответ потерян».

Сохранённый `backend_reference` также не становится автоматически
`snapshot.provider_location`. В `_step_finish()` обновляются состояние
snapshot/resource и ссылка шага. Поэтому отдельно определить, откуда
последующие revert/delete получают native snapshot ID. Если требуется новое
защищённое хранилище соответствий, описать его схему, порядок записи,
авторизацию, очистку и миграции отдельным изменением. Не подменять это
изменяемыми пользовательскими metadata или словарём процесса.

Повторный revert того же snapshot — новая операция с новым step UUID.
Признак завершения предыдущего revert нельзя использовать как успех нового.
Если история операций исчезла, безопасный исход остаётся `unknown`.

## 8. Как дорабатывать Huawei

### 8.1. Повторно использовать имеющийся код

В архивном `HuaweiBaseDriver` есть native create/activate и stop/delete,
проверки LUN и snapshot и работа с provider identity. Собственного
`revert_to_snapshot` в этой архивной версии нет. В отдельно исследованном
официальном драйвере есть native rollback; его реализация не входит
автоматически в наши 40 патчей.

Рекомендуемый объём: добавить checkpoint-методы в общую часть драйвера,
выделить нужные REST-операции и строгую интерпретацию ответов, сохранив
совместимость обычных volume/snapshot/attachment операций.

### 8.2. Составить карту REST-вызовов

Ниже — уже исследованные вызовы из официального драйвера v26.2.0. Это карта
для сверки с REST Reference целевой версии, а не универсальная спецификация
всех Dorado. Подробные ссылки на методы и исходные наблюдения находятся в
[исследовании Huawei](research/2026-10-08-dorado-without-hardware.md).

| Действие | Вызов относительно базового URL устройства |
|---|---|
| Создать snapshot | `POST /snapshot` |
| Активировать | `POST /snapshot/activate` |
| Остановить | `PUT /snapshot/stop` |
| Удалить | `DELETE /snapshot/{id}` |
| Начать rollback | `PUT /snapshot/rollback` |
| Прочитать объект | `GET /snapshot/{id}` |
| Найти по имени | `GET /snapshot?filter=NAME::{name}&range=[0-100]` |

Для каждого вызова зафиксировать типы и обязательность полей, ограничения
имени, привязку к parent/vStore, пагинацию, допустимые состояния, коды отказа,
правила timeout и подтверждение завершения. Числовые статусы брать из
документации выбранной версии; неизвестный код не считать успехом.

В официальном [flow rollback](https://github.com/Huawei/OpenStack_Driver/blob/bda6d13cd0147648e04da5479d678dc2e0541395/Cinder/Epoxy/huawei_flow.py#L918-L976)
используются `HEALTHSTATUS`, `ROLLBACKRATE`, `ROLLBACKENDTIME`.
Для нашего query нужны строгие проверки наличия полей и связи с текущим
шагом. Копировать условие с `dict.get()` без проверки отсутствующего значения
нельзя: неполный ответ может быть ошибочно принят за завершение.

### 8.3. Устранить повтор мутации после потери ответа

Архивный `RestClient.call()` после connection/auth error может выполнить
login и повторно отправить исходный запрос. Для checkpoint нужна отдельная
политика выполнения: неоднозначный исход POST/PUT/DELETE сохраняется как
`unknown`, а последующие действия сначала устанавливают результат чтением.
Проверить также retries HTTP adapter, redirects, relogin и переключение
controller URL. Обычную политику драйвера менять только при необходимости
и с отдельными регрессионными тестами.

Серверная идемпотентность могла бы разрешать повтор, но её нужно подтвердить
документацией для тех же request key, payload, ресурса и срока хранения ключа.
Общий заголовок request ID для трассировки не равен такой гарантии.

### 8.4. Решить восстановление составных операций

Create включает `create → activate`, delete — `stop → delete`.
C1/C1.1 claim выполняет только для `prepared` шага. Recovery для уже
отправленного шага вызывает исключительно query.

Если процесс погиб после create до activate, нельзя возвращать `succeeded`
только потому, что snapshot найден. Нельзя и запускать activate из query:
это новый внешний эффект. Обычная компенсация удалением snapshot при ошибке
activate тоже должна быть заменена согласованным журналируемым поведением.

Из документации нужно установить один из вариантов:

1. Есть подходящая серверная составная операция с долговечным идентификатором
   и возможностью прочитать её терминальный результат.
2. Нужны отдельные долговечные подшаги и право продолжения недостающей мутации.
   Тогда сначала проектируется расширение journal/continuation, его SQL/RPC
   границ и recovery, а затем подключается драйвер.

Второй вариант пока не реализован и не утверждается этим руководством как
готовый «C1.2». До разрешения развилки соответствующий профиль остаётся
неподдержанным. При этом транспорт, parser и документированные primitives
можно разрабатывать и тестировать независимо.

## 9. Как дорабатывать TATLIN

Начать с документации выбранной версии TATLIN и соответствующего драйвера.
В архивном `TatlinCommonVolumeDriver.create_snapshot()` вызывается клонирование
с полным копированием данных. Это не подтверждает `native_snapshot` с
`snapshot_semantics=cow|row`, обязательный для нашего контракта.

Необходимые действия:

1. Найти документированный native snapshot/revert API либо версию драйвера,
   которая его использует. Зафиксировать модель, firmware/API и лицензию.
2. Установить, разрешён ли откат выбранного старого snapshot в исходный том,
   что происходит с другими снимками, LUN identity и FC/iSCSI exports.
3. Определить request/job identity и чтение результата после потери ответа.
4. Реализовать пять методов в общей части драйвера, переиспользуя подходящие
   подключения и идентификацию томов.
5. Проверить `TatlinClientCommon._access_api()`: он обёрнут в retry по
   исключениям. Для неоднозначных checkpoint-мутаций требуется отдельный путь
   без слепого повтора.
6. Пройти те же проверки контракта и восстановления, что для Huawei,
   затем отдельно проверить FC и iSCSI, заявленные профилем.

Полное копирование нельзя переименовать в native snapshot сменой capability.
Ограничение относится к предоставленному исходнику, а не ко всем версиям
TATLIN. Сведения из документации Huawei не доказывают поведение TATLIN.

## 10. Как оформить сведения из документации

Для каждого вывода хранить запись следующего вида:

```text
Требование Cinder: operation_reconciliation
Модель и версия документа: ...
Название документа, раздел, URL/страница: ...
Документированное поведение: ...
Метод драйвера и способ реализации: ...
Окна сбоя и ожидаемый readback: ...
Тесты на синтетических ответах: ...
Проверка на массиве: не выполнена / ссылка на отчёт
Открытый вопрос: ...
```

Минимальные вопросы к документации Huawei:

- Есть ли client request key, дедупликация мутаций и lookup по этому ключу?
- Как отличить новый rollback от завершённого ранее rollback того же snapshot?
- Каковы срок хранения job history, правила eventual visibility и поведение
  после failover/restart контроллера?
- Есть ли серверный create-and-activate и терминальный результат этой операции?
- Как подтверждается завершение delete и отсутствие ещё выполняющегося запроса?
- Сохраняются ли остальные snapshots, исходные LUN/WWN и mappings при rollback?
- Какие ограничения накладывают writable/cascaded snapshots, replication,
  HyperMetro и consistency groups?

Это вопросы для поиска доказательств, а не утверждения об отсутствии функций.
Когда документация даёт однозначный ответ, его следует использовать в
реализации и тестах. Стенд проверяет фактическое выполнение этого контракта.

## 11. Порядок реализации и локальные проверки

Сначала проверить схему запросов и ответов, затем recovery, после этого
подключить hooks к Cinder. Новые тесты должны вызывать будущий реальный
vendor adapter с контролируемым HTTP-сервером/транспортом. Существующий
`FakeCheckpointDriver` проверяет общую модель Cinder и сам по себе не
подтверждает правильность Huawei/TATLIN.

| Проверка | Обязательный результат |
|---|---|
| Неизвестный профиль, firmware или свойства тома | Отказ capabilities до мутации |
| Неполные поля, неверные типы, неизвестный vendor status | Нет ложного success/no-effect |
| Тот же step UUID и payload | Нет повторного отправления того же внешнего эффекта |
| Тот же UUID, но другой том/snapshot/action | Отказ до I/O |
| Потеря ответа после выполнения записи | `unknown`, затем query; счётчик мутаций не увеличивается |
| Query на любом этапе | Только наблюдение, без create/activate/rollback/delete |
| Чужой parent/WWN/vStore, неоднозначный поиск | Нет присвоения или удаления чужого объекта |
| Смерть worker до/после dispatch и сохранения ответа | Восстанавливается исходный шаг; нет нового destructive dispatch |
| Сбой между create/activate и stop/delete | Нет ложного завершения; соблюдается выбранная модель подшагов |
| Старое завершение rollback или исчезнувшая история jobs | Не принимается за успех текущего шага |
| Частичный revert двух томов | Защита сохраняется, смешанный набор не выдаётся как завершённый |
| Drift профиля после reserve | Выполнение отклоняется без снятия защиты |
| Обычные snapshot/volume/attachment операции | Сохраняется прежнее поведение |
| Сервисное продолжение C1.1 после истечения user token | Проверяется scope исходного владельца; глобальный admin context не требуется |

Сохранять исходные запросы без credentials, счётчики native writes, состояния
SQL и идентификаторы шага. Разделять synthetic fixtures, реальные captures
и результаты hardware qualification. Локальный D1-P из прежней работы
может быть материалом для тестов протокола, но он не Cinder adapter и не
доказательство долговечного recovery или текущего rollback UUID.

## 12. Команды существующих тестов

Команды ниже предназначены для подготовленной Linux-среды с Python 3.11,
tox 4, системными зависимостями Cinder и доступом к зависимостям этого форка.
Рабочий каталог — Cinder checkout с патчами. `tox.ini` использует constraints
OpenStack 2025.1; точный набор зависимостей следует закрепить для сравнения
baseline и изменённой версии.

В `requirements.txt` есть закрытый `storage_client>=1.3`. Если он недоступен,
согласовать и записать отдельный ограниченный набор зависимостей и тестов.
Историческое исключение SberCloud не означает полного прохождения исходного
набора и не должно молча переноситься в новый отчёт.

```sh
# Общие unit tests checkpoint C1/C1.1.
tox -e py311 -- --concurrency=1 'cinder\.tests\.unit\.checkpoints\.'

# Регрессия существующих драйверов Huawei и TATLIN.
tox -e py311 -- --concurrency=1 'cinder\.tests\.unit\.volume\.drivers\.(huawei|yadro)\.'

# WSGI/SQL/RPC functional tests общего контракта и continuation.
tox -e functional-py311 -- --concurrency=1 'cinder\.tests\.functional\.test_checkpoint_(contract|continuation)\.'

# Аутентификация сервисного продолжения.
tox -e py311 -- --concurrency=1 'cinder\.tests\.unit\.api\.middleware\.test_checkpoint_continuation_auth\.'

git diff --check
```

Это команды существующих наборов из текущего `tox.ini`; при подготовке данного
руководства они заново не запускались. Тесты будущих hooks добавить в
vendor test-каталоги и проверить, что их IDs попадают в отчёт. Не засчитывать
пустой inventory или пропущенные DB/backend tests как успешную проверку.
Гонки SQL дополнительно воспроизводить на выделенных тестовых MySQL/PostgreSQL,
с теми же настройками баз в baseline и изменённой версии.

После целевых проверок выполнить широкий regression Cinder, проверить
изменённые файлы линтером и документацию. Исторические исходные замечания
сравнивать с baseline; новые ошибки не маскировать общим исключением.

## 13. Проверка на массиве и затем с Nova

Сначала проверить дисковый контракт на явно выделенных тестовых LUN:

1. Записать данные A, создать snapshot A; сохранить Cinder/native IDs и hashes.
2. Записать B, создать snapshot B; затем записать C.
3. Откатить A, проверить данные A и прежний исходный LUN; убедиться,
   что B остался доступен.
4. Откатить B, затем повторно A. Для каждого revert должен быть новый step UUID
   и отдельное подтверждение исхода.
5. Удалить одну точку и проверить оставшуюся, текущие данные и mappings.
6. Повторить с потерей ответа, restart worker и поддерживаемыми сценарием
   сбоями контроллера; сопоставить реальный эффект с журналом Cinder.

Затем выполнить сквозной сценарий на одной явно выбранной ВМ с реальными
Cinder-дисками: разные метки в RAM и на дисках → checkpoint → изменение обоих
состояний → откат той же ВМ → проверка прежних меток, UUID, LUN/WWN,
подключений и остальных точек. RAM должна восстанавливаться через существующий
Nova executor. Для частично восстановленного набора дисков нельзя заявлять
готовность к unpause.

Готовность драйвера не включает автоматически readiness libvirt, RAM-store,
staging, профилей и полной topology Nova. Для них использовать
`doc/source/admin/instance-checkpoint-executor.rst` и
`doc/source/admin/instance-checkpoint-qualification.rst` в Nova после патчей.
Включение функции и миграции БД выполнять отдельным этапом внедрения;
значение по умолчанию остаётся `enabled=false`.

## 14. Что передавать по завершении доработки

| Артефакт | Что должно быть внутри |
|---|---|
| Серия патчей поверх C1.1 | Реализация одного выбранного драйвера, тесты, документация; отдельные изменения общего контракта, если они понадобились |
| Карта соответствия документации | Версии/ссылки, подтверждённые гарантии, unresolved вопросы и выбранная модель recovery |
| Локальный отчёт | Точный commit/tree, зависимости, test IDs, результаты, причины пропусков и сравнение с baseline |
| Стендовый отчёт | Модель/firmware/pool/transport, тестовые ресурсы, captures и hashes; отдельный статус, если стенд ещё не запускался |
| Профиль поддержки | Только реально проверенная конфигурация; unknown profiles продолжают отклоняться |
| Runbook | Обновление, наблюдение за unknown, диагностика и завершение операций без ручного удаления locks |

После коммита проверенной доработки сформировать новую серию, не меняя
существующие 40 патчей:

```sh
git format-patch --output-directory ../driver-patches checkpoint-c11-base..HEAD
git rev-parse 'HEAD^{tree}'
```

Применить новую серию к отдельному чистому C1.1 checkout, сверить итоговый
tree, затем записать порядок применения и SHA-256. Два результата явно
разделять: «код реализован и локально проверен» и «профиль прошёл проверку
на массиве». Документация Huawei позволяет двигаться к первому результату
уже до появления оборудования.
